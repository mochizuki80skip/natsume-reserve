# 更新ファイル（zip）を作って渡す

## いつ使うか

画面やサーバーの変更をコミットし、確認テストが通ったあと。依頼者は zip をレンタルサーバーのファイルマネージャーで上げます（GitHub Actions の自動反映を使っていない場合）。

## 手順

1. 変更をすべてコミットする（`scripts/make-update.sh` は、コミットしていない変更があると止まる）。
2. 前回「まるごと」入れた時点のコミット（BASE）を確かめる。分からなければ依頼者に最後に上げた zip の名前を聞き、その時点のコミットを使う。
3. 作る：
   ```bash
   scripts/make-update.sh <BASE> <出力先フォルダ> update-$(TZ=Asia/Tokyo date +%m%d)a
   ```
   同じ日の 2 つ目からは末尾を b, c, … にする。
4. 中身を確かめる：
   - `1_assets` に js と css が 1 つずつ（`public/index.html` が読むもの）
   - `2_app` に `config.php` が無い
   - `3_root/version.json` の `version`（＝画面の版）と、画面の js に入っている版が同じ（スクリプトが確かめる）
   - 前に渡した zip の内容もすべて入っている（BASE からの差分なので、途中の zip を上げていなくても最新の zip だけでよい）
5. `SendUserFile`（`display: attach`）で zip を渡す。

## 依頼者への伝え方（例）

> 更新ファイル **update-1028a.zip（画面の版 2026-10-28 11:49）** をお送りしました。いつもの順番で上げてください。
> 1. `1_assets` の中身 → `assets` フォルダへ
> 2. `2_app` の中身 → `app` フォルダへ（同じ名前のファイルは上書き）、`2_guide` の中身 → `guide` フォルダへ
> 3. 最後に `3_root` の 3 つのファイル → いちばん上のフォルダへ
> 上げたあと、画面の右下の「画面の版」が 2026-10-28 11:49 になっているか確かめてください。

- 変わったサーバー側のファイル名を書き添える（例：「`2_app` で変わったのは `lib/Karte.php` だけです」）。
- DB の項目が増えたときは「データベースの項目は自動で足されます」と伝える（最初のアクセスで `Migrate` が動く）。
- `3_root` を最後にするのは、新しい画面が古いサーバーのファイルを呼ばないようにするため。

## 注意

- `public/version.json` が確認用の版（`2099…`）のまま作らない（スクリプトが止める）。
- `config.php`・本物の個人情報・テストの出力（`e2e/out-*`）を入れない。
- 1 つの zip にまとめて渡し、途中の版の zip を上げ忘れても困らないようにする。
